# ЛР № 10 руками: как показать

Сдаём на 6 баллов: интеграционные тесты с Testcontainers работают, Locust показывает RPS
и latency, нагрузка выявляет узкое место. Порядок — как в разделе «Что сдавать» методички,
пункты 1–4. Только стандартные инструменты: `pytest`, `docker`, `psql`, `curl`
и веб-интерфейс Locust.
Скрипт `scripts/load_stand.sh` только поднимает стенд: контейнеры и API с нужными настройками.
Каждый шаг прогнан на этом ноутбуке. Цифры нагрузки от прогона к прогону немного плавают.

## 2. Как работает Testcontainers (пункт 2)

Открыть `tests/integration/conftest.py`:

- строка 29 — образ `postgres:16-alpine`, тот же, что в `docker-compose.yml`;
- строка 34, `postgres_url` — контейнер поднимается один раз на сессию тестов;
- строка 49 — схема накатывается `alembic upgrade head`, как в проде, а не `create_all()`;
- строка 71 — перед каждым тестом `TRUNCATE ... RESTART IDENTITY`: база чистая, id с единицы.

Откат транзакции, как в методичке, здесь не сработает: обработчик заказа сам делает `commit`,
откатывать после теста нечего.

### Тест ловит настоящий баг

Последний тест нашёл гонку: два параллельных заказа оба проходили, баланс уходил в минус.
Исправление — блокировка строки пользователя. Если её убрать, тест падает.

Открыть `app/modules/orders/repository.py`, строка 52, и удалить из вызова
`with_for_update={"of": UserModel}, `. Должно остаться:

```python
        row = self.db.get(UserModel, user_id, populate_existing=True)
```

```bash
pytest tests/integration/test_orders_postgres.py -v
```

Ответ: `1 failed, 4 passed`, у `test_parallel_orders_do_not_overspend`
`AssertionError: assert ['ok', 'ok'] == ['ok', 'rejected']`: прошли оба заказа.
Вернуть файл:

```bash
git checkout app/modules/orders/repository.py
```

На SQLite в памяти, где идут остальные 361 тест, эту гонку не увидеть: там одно соединение
на все потоки.

## 3. Locust: RPS и latency под нагрузкой (пункт 3)

Два терминала: A — API, B — Locust.

Терминал A, по очереди:

```bash
scripts/load_stand.sh up
```
```bash
WORKERS=1 scripts/load_stand.sh api
```

Первая команда поднимает PostgreSQL и Redis в Docker, вторая — API на порту 8020.
Готово, когда появилась строка `Uvicorn running on http://127.0.0.1:8020`.

Терминал B:

```bash
locust -f locustfile.py --host=http://127.0.0.1:8020
```

Открыть в браузере http://localhost:8089 и ввести:
Number of users — `50`, Ramp up — `10`, нажать **START**.

Locust изображает студентов: каждый раз в 1–3 секунды открывает меню, иногда карточку блюда,
иногда делает заказ. На вкладке **STATISTICS** смотреть строку **Aggregated**:

| Колонка | Что значит |
|---|---|
| Current RPS | сколько запросов в секунду API успевает обработать |
| 95%ile (ms) | 95% запросов быстрее этого времени |
| # Fails | сколько запросов с ошибкой |

Поднимать нагрузку: **EDIT** → вписать новое число студентов → **Update**, потом **RESET**,
чтобы цифры считались заново. Ступени: 200, 400, 600, на каждой подождать минуту.

Что примерно будет:

| Студентов | RPS | 95%ile | Ошибки |
|---|---|---|---|
| 50 | ~20 | десятки мс | 0 |
| 200 | ~90 | десятки мс | 0 |
| 400 | ~150–190 | от десятков до сотен мс | 0 |
| 600 | падает до 10–40 | 10 000 мс | растут |

До 400 всё нормально. На 600 система ломается: RPS падает, ответы идут по 10 с (это таймаут
Locust), на вкладке **FAILURES** — `ReadTimeout`. Иногда это начинается уже на 400.

## 4. Узкое место и как его нашли (пункт 4)

В Locust — **STOP**. Нагрузки уже нет. Проверить API в терминале B (Locust можно оставить,
открыть новую вкладку терминала):

```bash
curl -m 10 http://127.0.0.1:8020/menu/items
```

Ответа нет: через 10 с `curl: (28) Operation timed out`. API завис.

Что с базой:

```bash
docker exec lab10-pg psql -U sirius -d sirius_food -c "select state, count(*) from pg_stat_activity group by 1"
```

В ответе строка `idle in transaction | 15`: все 15 соединений с базой заняты, но ими никто
не пользуется.

Что сказать:

**Узкое место — один процесс API.** Python в одном процессе выполняет код в одном потоке за раз
(GIL), поэтому API может занять только одно ядро. На 400 студентах процессор загружен на 94%,
запросы копятся в очереди. Дальше у API кончаются два ресурса сразу: 40 потоков и 15 соединений
с базой. Соединения держат запросы, которые ждут свободный поток, а потоки заняты запросами,
которые ждут соединение. Все ждут друг друга, API висит.

**Как нашли:** задержки и ошибки — в Locust, зависшие соединения — в базе (запрос выше),
загрузка процессора — замер в `docs/lab10/load/RESULTS.md`. Кто чего ждёт, показал дамп потоков:
все 40 потоков ждут соединение с базой (`docs/lab10/load/baseline/thread_dump.txt`).

**Как лечится:** 4 процесса API вместо одного и больше соединений с базой. После этого 600
студентов идут с ответом за 59 мс и без ошибок, предел — около 1600. Цифры до и после —
`docs/lab10/load/RESULTS.md`.

Grafana из ЛР № 9 здесь не подключена: API запущен процессом на хосте, а не в контейнере.
Метрики те же: задержка, процессор, соединения с базой.
